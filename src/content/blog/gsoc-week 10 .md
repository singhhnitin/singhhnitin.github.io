GSoC Week 10: Being Precise About Evaluation, Testing Few-Shot Prompting, and Organizing the Codebase

This week focused on transparency and rigor — documenting exactly how every evaluation number is produced, testing whether few-shot prompting could improve results, and making sure the whole project's code and documentation genuinely live in one organized, discoverable place.

Being Exact About How F1 Is Calculated

Before sharing more results, it's worth being fully precise about what every F1 number in this project actually measures. For each sentence, predicted triples are checked against the gold (correct) triples — subject, relation, and object all need to match for a triple to count as correct. Precision is correct triples divided by everything predicted; recall is correct triples divided by everything in the gold answer; F1 combines the two into one balanced number. This is computed per sentence, then averaged across every sentence in a given source.

One detail worth being clear about: "property"-type triples — descriptive fragments rather than real relational facts, around 74% of everything extracted — are excluded from this scoring on both sides. F1 measures how well the pipeline handles genuine facts specifically, not the descriptive fragments set aside from DBpedia matching.

Where the gold answer itself comes from also matters, and is worth stating plainly: for the Wikipedia and Train sources, the "correct" triples were generated by an LLM during data creation, then kept only if a separate judge model scored them highly. So F1 on these two sources is really measuring agreement with another model's judgment, not verification against human-confirmed ground truth. BenchIE is different and genuinely independent — its subject/relation/object spans were human-verified in earlier project years, with only the DBpedia property mapping layer added this year. This makes BenchIE the stricter, more trustworthy of the three measurements, and is very likely part of why its F1 score reads lower than the other two — it may be showing a more honest picture of real-world performance, not simply being a harder test.

Testing Few-Shot Prompting

The current pipeline runs zero-shot, with no examples shown to the model at inference time. This week tested whether giving the model example sentences beforehand would improve results.

Random few-shot — three fixed examples, picked at random from the training set and shown before every test sentence — performed worse than zero-shot on every single source tested. This matches a real, published finding directly: a peer-reviewed paper on this exact question (AgentRE, CIKM 2024) found that randomly-selected examples barely help at all, while examples chosen specifically for their relevance to the sentence being tested help meaningfully. This project's result lines up closely with that paper's "random barely helps" finding — a reassuring sign that the result reflects a known, real pattern rather than something specific going wrong.

Similarity-based few-shot — a different, freshly retrieved set of 5 examples for every single test sentence, chosen by genuine similarity to that sentence using the project's existing embedding model — gave a more interesting, mixed result: it under-performed zero-shot on Wikipedia and Train, but was the only approach that actually improved BenchIE, moving it from 0.173 to 0.184. Since BenchIE is the source with the most trustworthy, independent gold data, this is a genuinely meaningful signal, even though the overall picture across all three sources is mixed rather than a clean win. Checking the retrieved examples directly suggested they were often similar in sentence shape rather than topic — a useful, concrete lead for anyone refining this approach further.

Organizing the Codebase Properly

The project's GitHub repository was reorganized this week so that every script that produced a real result lives in a clear, documented folder structure — training scripts, inference scripts, evaluation tooling, data-quality auditing, the human review app, ontology reference data, and results summaries each in their own place, with full project documentation in the README. Nothing important is only sitting on a personal server anymore; it's all tracked, versioned, and discoverable.

Two Open Design Questions Worth Documenting

Subject and object editing in the review tool. The current interface lets a reviewer type a corrected subject or object directly into a free-text box when the extraction got it wrong. An open question worth exploring further: would a dropdown — showing only words already present in that specific sentence — be a better default, since it would prevent typos and keep corrections consistent with the actual source text? Free text has the advantage of allowing a correction even when the right entity wasn't extracted as a separate span at all. Both approaches have a real, legitimate use case, and it's worth deciding deliberately rather than by default.

Documenting the pipeline visually. Two diagrams were built this week to make the full system understandable at a glance — the end-to-end pipeline from raw Wikipedia text through quality scoring, coreference resolution, extraction, normalization, human review, and feedback, and a detailed view of the predicate-linking sub-pipeline specifically (cache lookup, embedding retrieval, LLM disambiguation, final linked property).

Progress on DBpedia Ontology Mapping

Alongside the extraction pipeline work, real progress was made on the DBpedia Mappings Wiki side of the project this week: understanding that Hindi Wikipedia infobox fields aren't yet connected to DBpedia's ontology the way English infoboxes are, with "Infobox person" identified as the starting point for building those connections. A Mappings Wiki account was created and official edit access requested.

Looking ahead, the next round of work planned includes splitting every evaluation number into extraction-only and full-pipeline figures separately, and establishing genuine baselines — an existing external Hindi extraction tool, and the base model before any fine-tuning — on that same evaluation split, to give every result in the project a clear, honest point of comparison.
